## Analysis

Analysed on 16 Sep 2026 by Claude Code (Claude Opus 5).

Paul reported it from a live client site: *"Hey, we noticed you have been using 404 to 301
for some time … give it a 5-star rating on WordPress"*, shown in the admin notice area on
every admin screen except the plugin's own.

One rule. The rest of what 4.0.4 shows is about redirects and 404s on the site, a
migration it has just done, or cross-selling confined to its own menu and screens.

## Deliberately left alone

### The "Recent 404s" dashboard widget, and its cross-sell line

The widget lists the site's own top 404s over the last 30 days. That is real, local data.
When there are rows, the admin can `install_plugins` and Broken Link Checker is not
active, the footer adds one link: *"Find the links causing these"*, to the vendor's BLC
landing page.

**Mixed output, so no rule.** `remove_meta_box( 'd404_recent_404s', … )` would take the 404
data with it, and the promo is printed from a `private` method in the same render call,
with no hook in between. One arguably relevant link does not justify removing real site
data.

### `PromoMenu` — the rotating cross-promotion submenu

A submenu item under the plugin's own Redirects menu that advertises a different AIOSEO
product each week (SEO, Broken Links, Privacy Compliance, Backups, Spam Protection), with a
landing page for each. It is in the admin menu, not the notice area or the dashboard, and
the whole thing lives in the vendor's own menu. **Out of scope by construction.** It
writes `aioseo_404_to_301_promo_menu` to cache the week's choice. Uninstall leaves that
option behind.

### `Admin::suppressForeignNotices`

On its own screens, the plugin removes *other plugins'* notices from the four notice
hooks. It does not affect this project's rules, and it is not ours to change. Noted
because a debug session on a 404 to 301 screen will see notices "missing" that no rule of
ours removed.

### 3.x review notice — `JJ4T3_Admin::review_notice`

3.1.5 has its own review nag. Its callback returns early unless `$_GET['page']` is one of
`jj4t3-settings`, `jj4t3-logs` or `jj4t3-logs-addons`, so it **only renders on the vendor's
own screens**. Out of scope, and 3.x is superseded. No rule.

## Mechanism

- tier: 2 (targeted unhook, via the sanctioned `$wp_filter` reader)
- phase: `admin_init` at `self::LATE_PRIORITY`, in `unhook_vendor_notices()`
- vendor registers at: the main plugin file ends `aioseo404To301();`, which builds the
  `FourNotFour` singleton at plugin load. `init()` → `load()` →
  `$this->admin = new Admin\Admin();`. That constructor runs `new Notices\Review();`,
  which adds `admin_notices` → `maybeShowNotice` at priority 10. The hook is there
  before `admin_init`
- instance reachable via: **no.** `aioseo404To301()->admin` is public and reachable, but
  `Admin`'s constructor does not store the `Review` object. It stores `page` and nothing
  else

`maybeShowNotice` is the gate *and* the renderer, and it adds `printScript` to
`admin_footer` itself, only when it shows the notice. Removing `maybeShowNotice` therefore
removes the script too. **Do not add a second removal for `printScript`**: it is never
registered unless the notice has already rendered.

### Version history — why the rule only matters from 4.0.4

| Version | Review notice |
|---|---|
| 3.1.5 | `JJ4T3_Admin::review_notice`, vendor screens only (above) |
| 4.0.1, 4.0.2 | none |
| 4.0.3 | `Notices/Review.php` ships but **nothing calls it**, so it never renders. The vendor's own 4.0.4 docblock says so |
| 4.0.4 | the constructor hooks `admin_notices` itself, and the nag appears on every admin screen except the vendor's own |

Against 4.0.1 to 4.0.3 the rule finds nothing and logs
`… not registered on admin_notices; no action taken.` That is correct, not drift.

## Drift check

- `app/Admin/Notices/Review.php` — constructor still `add_action( 'admin_notices', [ $this,
  'maybeShowNotice' ] )`. If the vendor moves it back under a notifications centre (the
  docblock says the class "was written to be driven by an `Admin\Notifications` renderer, as
  it still is in the other plugins"), the target changes
- `app/Admin/Admin.php` — if `new Notices\Review()` is ever stored on a property, **drop the
  reader and name the instance**
- Namespace `AIOSEO\FourNotFour`. All in One SEO's own review notice is
  `AIOSEO\Plugin\Common\Admin\Notices\Review`, so they are separate classes. This rule does
  not cover AIOSEO; see `all-in-one-seo-pack.md`

```bash
unzip -p /vault/backups/wordpress/plugins/404-to-301/404-to-301,<version>.zip \
  404-to-301/app/Admin/Notices/Review.php | command grep -n "add_action\|^namespace\|^class"
```

## Verification

Bench: `bench2.local`, WP 7.1, 404 to 301 **4.0.4** unzipped from the vault,
16 Sep 2026. Before = 1.28.0 (HEAD), after = working copy, `HEADWALL_NAG_CLEANUP_DEBUG` on,
three warm-up requests after each deploy.

Time gate: `internalOptions->internal->firstActivated` must be more than two weeks old. It
is stored JSON-encoded in `aioseo_404_to_301_options_internal`, so `wp option patch` cannot
reach it. It was backdated 30 days with `wp eval` (`json_decode`, set, `wp_json_encode`,
`update_option`). The notice also needs `edit_posts` and a screen that is not the vendor's.

### Review request — **Confirmed** (bench)

| Check (dashboard and plugins.php) | Before | After |
|---|---|---|
| `d404-review-plugin-cta` | **5** | **0** |
| Debug log | — | `404-to-301: Removed AIOSEO\\FourNotFour\\Admin\\Notices\\Review::maybeShowNotice from admin_notices priority 10.` |

(Five matches: the notice's class, plus four in the printed dismiss script and its CSS. The
script going to 0 confirms the `printScript` point above.)

### Negative checks

| Check | Result |
|---|---|
| Screens asserted: `id="dashboard-widgets"`, `id="the-list"` | yes |
| `d404_recent_404s` widget still on the dashboard | yes |
| `_aioseo_404_to_301_plugin_review_dismissed` user meta | absent — nothing written |
| PHP fatals / warnings / parse errors | **0** |

`RedundantAddons` could not be exercised: it needs an upgrade from a site that had the old
addon plugins. It is a separate class and callback, and no rule names it.

gone the same day.
